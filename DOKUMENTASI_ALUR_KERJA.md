## 2. Google Drive — Struktur & Efek

### 2.1 Struktur folder

Semua berkas siswa tersimpan di **akun Google pemilik aplikasi** (`vworksofficial@gmail.com`), kuota 15GB gratis akun tersebut. OAuth bertindak sebagai pemilik file, sehingga kuota service account (0 byte) tidak menjadi masalah.

```
My Drive (vworksofficial@gmail.com)
└── VSV.VentureGo.id [database]/               ← ROOT (sebelumnya `VentureGo Berkas`, di-rename in-place)
    ├── Budi Santoso - LPK Sakura/             ← folder DRAFT, warna MERAH (menunggu persetujuan)
    │   ├── KTP - Budi Santoso.pdf
    │   └── Pas Foto - Budi Santoso.jpg
    ├── VSV-0001-2026 - Budi Santoso/          ← siswa resmi (status ACTIVE): rename + warna HIJAU
    │   ├── KTP - Budi Santoso.pdf
    │   └── KK (Kartu Keluarga) - Budi Santoso.jpg
    └── Siti Rahayu - LPK Harapan/             ← pemohon lain (folder terpisah per Firebase UID)
```

- **Root** `VSV.VentureGo.id [database]`: dibuat otomatis oleh aplikasi di root My Drive (scope `drive.file` — aplikasi hanya melihat file buatannya sendiri). Bila yang ditemukan masih bernama lama `VentureGo Berkas`, aplikasi **mengganti namanya di tempat** (folder ID dan seluruh isi tetap sama) pada akses pertama. Override opsional via env `GDRIVE_ROOT_FOLDER_ID`.
- **Satu folder per Firebase UID**: folder dibuat sekali per UID (tidak dicari berdasarkan nama), dipetakan di `driveFolders/{uid}`, dan dipakai ulang untuk semua pengajuan UID tersebut — dua siswa dengan nama & LPK sama tidak pernah berbagi folder. Saat memulai unggahan, server memeriksa bahwa folder mapping masih ada, belum masuk sampah, dan memang folder; bila referensinya sudah tidak valid, server membuat folder baru khusus UID tersebut dan memperbarui mapping. Berkas selalu berupa file langsung di dalam folder (tanpa subfolder) agar verifikasi kepemilikan saat submit tetap berlaku.
- **Folder draft (warna MERAH `#ff0000`)**: `<Nama Pemohon> - <Nama LPK>` (mis. `Budi Santoso - LPK Sakura`) — dibuat saat unggahan pertama pemohon, `stage: 'draft'`. Folder tetap merah dengan nama ini setelah pengajuan terkirim.
- **Folder siswa resmi (warna HIJAU `#00ff00`)**: saat status pengajuan menjadi **`ACTIVE`** (atau saat dokumen akad diterbitkan ketika status sudah `ACTIVE`), server (a) membaca **NIS** yang sudah diterbitkan saat terbit dokumen akad (`getExistingStudentNumber`), (b) **me-rename** folder menjadi `<NIS> - <Nama Pemohon>` (mis. `VSV-0001-2026 - Budi Santoso`), (c) mengwarnai hijau, (d) me-rename seluruh berkas di dalamnya ke pola nama standar, dan (e) memperbarui mapping `stage: 'active'`. Bila saat transisi ke `ACTIVE` NIS belum terbit, promosi ditunda hingga dokumen akad diterbitkan; perubahan status berikutnya tidak mengembalikan folder ke merah.
- **Unggahan susulan** (setelah pengajuan ada): langsung ke folder yang tercatat di `driveFolderId` aplikasi; folder dibuat bila belum ada (dengan nama & warna sesuai status aplikasi).
- **Nama file standar**: `<Jenis Dokumen> - <Nama Pemohon><ekstensi>` (mis. `KTP - Budi Santoso.pdf`, `Ijazah SMA - Budi Santoso.pdf`, `Akad Wakalah bil Ujrah - Budi Santoso.pdf`). Awalan `Scan ` dan bagian setelah `/` pada label dokumen dibuang; nama asli berkas dari pengguna tidak dipakai sebagai nama Drive.

### 2.2 Alur unggahan (chunked resumable)

1. Klien memanggil `POST /api/applicant/uploads` dengan header `x-upload-action: init` + token ID Google Firebase → server memvalidasi lalu membuat sesi resumable di Drive → mengembalikan `ticket` (HMAC, TTL 30 menit) + `chunkSize` 4 MB.
2. Klien mengirim potongan (`x-upload-action: chunk`, header `Content-Range`) — 4 MB per potongan (di bawah limit body Vercel 4,5 MB).
3. Potongan pertama **diverifikasi tanda tangan berkas** (magic byte PDF/JPG/PNG) — bila salah → sesi dibatalkan, error `Isi berkas tidak sesuai dengan formatnya.`
4. Potongan terakhir → file selesai → bila unggahan terkait pengajuan, transaksi Firestore menulis entri `documents[index]` `{documentType, status:'UPLOADED', fileId, fileName, mimeType, size}` + `driveFolderId`. Bila transaksi gagal, file di Drive **dihapus** (tidak ada file yatim).
5. Server **memverifikasi ulang** setiap `fileId` ke Drive saat submit — file yang tidak ada di folder milik pemohon akan menggugurkan pengajuan.
6. Error tak terduga pada route unggah mencatat tahap, aksi, jenis/kode error, dan ID referensi acak ke log server tanpa token, UID, nama berkas, atau isi dokumen; ID referensi ikut ditampilkan agar kegagalan localhost dapat dicocokkan dengan log.

### 2.3 Validasi & batasan

| Aturan          | Nilai                              | Pesan error (user-facing)                                                |
| --------------- | ---------------------------------- | ------------------------------------------------------------------------ |
| Tipe file       | PDF, JPG, PNG                      | `Gunakan berkas PDF, JPG, atau PNG.`                                     |
| Ukuran per file | maks **10 MB**                     | `Ukuran berkas maksimal 10 MB.` / `Ukuran setiap berkas maksimal 10 MB.` |
| Total ukuran    | maks **60 MB**                     | `Ukuran seluruh dokumen tidak boleh melebihi 60 MB.`                     |
| Isi file        | Cocok dengan ekstensi (magic byte) | `Isi berkas tidak sesuai dengan formatnya.`                              |
| Token sesi      | Harus akun Google & valid          | `Sesi unggah telah berakhir. Silakan muat ulang halaman.` (401)          |
| Ticket unggahan | HMAC, TTL 30 menit                 | `Sesi unggah tidak valid. Silakan ulangi unggahan.`                      |
| Scan KTP        | Wajib ada saat submit (2 produk)   | `Dokumen Scan KTP wajib diunggah.` / `Dokumen KTP siswa wajib diunggah.` |

### 2.4 Efek sisi Drive saat alur berjalan

| Aksi aplikasi                               | Efek di Google Drive                                                                                                                                             |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unggahan pertama (sebelum submit)           | Folder draft `<Nama> - <LPK>` **merah** dibuat di root (bila belum ada)                                                                                          |
| Submit pengajuan **berhasil**               | Nama/warna folder **tidak berubah** (tetap draft merah); mapping `driveFolders` → `stage:'submitted'`                                                            |
| Status pengajuan → **`ACTIVE`**             | Bila NIS sudah terbit: folder **di-rename** `<NIS> - <Nama>` + warna **hijau** + seluruh berkas di-rename pola `<Jenis> - <Nama>`; mapping → `stage:'active'`    |
| Admin menerbitkan dokumen akad (`.docx`)    | File `Akad Wakalah bil Ujrah [dan Jualah] - <Nama Pemohon>.docx` disimpan di folder pengajuan; bila status sudah `ACTIVE`, folder langsung dipromosikan ke hijau |
| Submit **gagal**                            | File yang baru terunggah **dihapus** otomatis (`discardDriveUploads`)                                                                                            |
| Ganti dokumen di unggah-berkas              | File baru ditulis dengan nama `<Jenis> - <Nama Pemohon>`; **file lama tidak dihapus** oleh sistem (lihat §8)                                                     |
| Admin mengunggah PDF akad                   | File `Akad Wakalah bil Ujrah - <Nama Pemohon>.pdf` disimpan di folder pengajuan (versi lama tetap ada)                                                           |
| Admin mengunduh dokumen                     | Stream dari Drive (`GET /api/admin/.../documents/[index]`), tidak ada URL publik                                                                                 |
| Akses kedaluwarsa (token OAuth kadaluwarsa) | Error 503 `Akses penyimpanan berkas kedaluwarsa. Silakan setujui ulang akses aplikasi.`                                                                          |

### 2.5 Kredensial (server-only, di Vercel & `.env.local`)

- `GDRIVE_OAUTH_CLIENT_ID`, `GDRIVE_OAUTH_CLIENT_SECRET` — OAuth client tipe _Desktop app_.
- `GDRIVE_REFRESH_TOKEN` — hasil klik **Allow** sekali oleh pemilik akun; server menukarnya jadi access token otomatis.
- Consent screen harus berstatus **Production** agar refresh token tidak kedaluwarsa 7 hari.
- Tidak ada kunci service account yang dipakai lagi untuk Drive.

### 3.3 Dashboard pemohon

Semua halaman dashboard memerlukan **login Google**. Selama sesi diperiksa tampil layar loading roket (`Menyiapkan akunmu…`); tanpa sesi aplikasi → diarahkan ke `/` (welcome). Akun staf (`vworksofficial@gmail.com`, `demo.admin@venturego.id`, atau allowlist) → diarahkan ke `/admin`. Pemohon baru yang sudah login tetapi belum punya pengajuan tetap melihat **kartu ringkasan default** di beranda. Navigasi bawah: **Angsuran · Riwayat · Beranda · Unggah · Profil**.

Halaman **Angsuran**, **Riwayat**, **Unggah Berkas**, dan **Profil** tidak menampilkan header atas/tombol kembali maupun judul-subjudul halaman. Konten langsung dimulai di bawah tepi atas layar; navigasi bawah tetap tersedia. Sebaliknya, sub-halaman Profil (`/dashboard/profil/data-diri|dokumen|akad|keamanan|persetujuan|kartu|tentang`) memakai header standar dengan judul + tombol kembali ke `/dashboard/profil`.

#### Beranda `/dashboard`

- Sapaan `Selamat datang, <nama depan>` (dari nama pemohon atau nama akun Google; loading: `Memuat…`), lonceng → notifikasi (titik amber tampil bila ada pengajuan aktif).
- **Kartu putih bisa digeser kiri/kanan** (`dashboard/_components/wallet-carousel.tsx`, CSS scroll-snap tanpa library, 3 titik penanda di bawah kartu yang juga bisa diketuk; hormati `prefers-reduced-motion`). Urutan halaman: **1. Ringkasan angsuran** (di bawah) → **2. Saldo Vworks Investment Partner** → **3. Poin VentureGo**. Tombol mata berlaku untuk ketiganya. Data halaman 2–3 dari `getWalletSummary` (`dashboard/vip/actions.ts`), dimuat paralel dengan ringkasan; selama dimuat tampil skeleton.
  - **Saldo VIP**: bila akun adalah mitra VIP → saldo dana (`principalBalance`), pil `VIP · Aktif`, `Bagi hasil terakhir` (nominal + tanggal), `Jadwal berikutnya` (tanggal 15 berikutnya, WIB) + tautan `Lihat riwayat →` ke `/dashboard/vip`. Bukan mitra → `Rp0`, pil `Belum terdaftar`, penjelasan singkat + `Pelajari VIP →`. Nominal bagi hasil berikutnya **tidak** diproyeksikan (bagi hasil mengikuti akad, bukan imbal tetap).
  - **Poin VentureGo**: jumlah `amount` di `pointLedger` milik UID (`{n} poin`, pil `Terkumpul`), teks `Poin terkumpul di akun Anda: {n} poin.` + chip `Penukaran hadiah segera hadir`. Sumber poin sengaja **tidak** disebut di layar pengguna. Penulisan poin belum ada — lihat `docs/usulan/2026-11-pembiayaan-berulang-dan-poin.md` §2.
- **Kartu ringkasan** (halaman 1): nominal (`Total kewajiban akad`/`Estimasi diajukan`), toggle sembunyikan nominal (`Rp••••••••`), **pil status**, progres bar `{paidCount} dari {total} angsuran lunas` + `Terbayar Rp…`, `Sisa angsuran: {total - paidCount} kali`, `Jatuh tempo berikutnya`; bila belum ada jadwal → `Berkas terunggah {x}/{y} ({verified} ✓)` + `Nomor pengajuan {VSV-APP-…}` (+ peringatan kuning bila ada dokumen berstatus `Perlu perbaikan`); bila biaya masih estimasi → `Rincian biaya sedang disusun dan diverifikasi tim VentureGo.`
- Saat sesi atau ringkasan Firestore sedang dimuat, nama akun, kartu ringkasan, badge progres, dan daftar tahap menampilkan skeleton pulse; tidak ada teks loading yang menggantikan susunan kartu.
- **Pengguna baru (sudah login Google) / tanpa pengajuan**: kartu ringkasan langsung tampil dengan nilai default — `Total angsuran terbayar` **Rp0**, progres 0% (`Belum ada pembayaran`, `Total kewajiban Rp0`), `Tenor` **0 bulan**, dan `Virtual Account` **0000000000000000**, dengan pil `Belum ada pengajuan`. Baris `Virtual Account` memakai komponen `VaNumber` (`dashboard/_components/va-number.tsx`): **tekan lama ±500 ms** pada angka atau **tombol salin di ujung kanan** label menyalin nomor (Clipboard API + fallback `execCommand`), lalu tampil teks singkat `Nomor VA disalin`. Selama nomor masih placeholder (kosong/semua nol) tidak ada yang disalin dan tampil `Nomor VA terbit setelah akad disetujui`. Komponen menerima `number` dan `bank` (label menjadi `Virtual Account · <Bank>`) untuk dipakai saat Fixed VA per siswa tersedia. CTA pengajuan tetap berada pada kartu `Ajukan Pembiayaan Baru` di bawah hero.
- **Alur progress saat ini** — 7 tahap: `Pengajuan → Verifikasi & kelayakan → Pengumpulan berkas online → Akad pembiayaan → Pencairan dana → Program angsuran → Pelunasan`, badge `Tahap {n}/7`, tahap aktif berchip `SEKARANG`; status tertutup (Ditolak/Dibatalkan) menampilkan catatan merah.
- Kartu `Ajukan Pembiayaan Baru` (→ `/?step=1`) dan `Layanan cepat` (Bayar angsuran, Simulasi, Ajukan baru, Bantuan, VIP).

#### Unggah berkas `/dashboard/unggah-berkas`

- Banner: `Unggah dokumen PDF, JPG, atau PNG. Maksimal 10 MB untuk setiap berkas.`
- Pemilih pengajuan bila >1 (`{VSV-APP-…} · {nama}`); dua grup: **Dokumen utama** dan **Dokumen pendukung**.
- Per slot: label (+ bintang merah untuk wajib), lencana status riil (`Sudah diunggah`, `Diverifikasi`, atau `Perlu perbaikan`), `{nama file} · {x,x} MB` atau `Belum diunggah`, tombol **`Unggah`** / **`Ganti`** / **`Perbaiki`** / `Mengunggah…` / `Belum aktif` (tanpa pengajuan).

#### Angsuran `/dashboard/angsuran`

- Hanya pengajuan **Dana Keberangkatan** dengan rincian biaya. Chip status: `Menunggu verifikasi` / `Penawaran terverifikasi` / `Akad disepakati` / `Pengajuan dibatalkan|ditolak`.
- Amber: `Estimasi total yang Anda ajukan: Rp… Angka ini bukan total Nafaqah/Ujrah terverifikasi atau nominal akad.`
- Bila `pricingStatus` = `VERIFIED`/`AGREED`: blok **Rincian kewajiban** (baris `Nafaqah · biaya riil` — nominal per baris tampil `—` bila nol dan totalnya mengikuti invoice LPK — + `Ujrah · jasa` dengan penerima & referensi bukti), total (Nafaqah, Ujrah tetap, Uang saku qardh, Refund/potongan, **Total akad**), **Jadwal angsuran** (`{n} kali`, tanggal, nominal, sisa setelah bayar), referensi akad final.
- **Persetujuan pemohon**: tombol `Saya menyetujui rincian terverifikasi` → `Persetujuan atas penawaran tercatat.`; bila sudah: `Penawaran sudah disetujui`. Bila `AGREED`: catatan hijau `Akad final tercatat disepakati. Total kewajiban tidak bertambah karena waktu atau keterlambatan. Pelunasan dipercepat tidak dikenai penalti.`
- **Permohonan keringanan**: textarea (10–1000 karakter) + `Kirim permohonan` → masuk daftar `Menunggu tinjauan` (maks 10 permohonan; ditinjau admin — §4.3).
- Belum diverifikasi: `Admin sedang menyusun dan memverifikasi rincian biaya. Nominal dari contoh akad tidak digunakan sebagai harga otomatis.`

#### Pembayaran `/dashboard/pembayaran`

- Info: `Pembayaran diproses di halaman aman Xendit. Tersedia Virtual Account (BCA, Mandiri, BNI, BRI) dan QRIS; status lunas dikonfirmasi otomatis.`
- Per pengajuan: baris `Angsuran {n}` + tanggal + nominal; lunas → `✓ Lunas`; tombol **`Bayar`** atau **`Lanjutkan`** (bila ada invoice PENDING masih berlaku).
- **Pembayaran bebas** (pelunasan sebagian/sukarela): pilih pengajuan + nominal (min Rp1.000, maks Rp100.000.000) → `Bayar {Rp…}`.
- **Riwayat pembayaran** + tombol `Segarkan`: status `Menunggu pembayaran` / `Lunas` / `Kedaluwarsa` / `Gagal`.
- **Alur Xendit:**
  1. Server membuat dokumen `payments` (`PENDING`) + invoice Xendit (durasi **48 jam**, IDR) → browser dialihkan ke `invoiceUrl` (halaman aman Xendit).
  2. Pemohon membayar via VA/QRIS.
  3. **Webhook** Xendit → `PAID`/`SETTLED`: pembayaran `Lunas` + (untuk angsuran) nomor angsuran ditambahkan ke `paidInstallments` aplikasi; `EXPIRED` → `Kedaluwarsa`. Callback ber-`external_id` `trm-` (VA Turrima) dan `vsv-` (VA/invoice siswa di app versi lama) **tidak diproses di sini** — diteruskan apa adanya (body & `x-callback-token` asli) ke `TURRIMA_WEBHOOK_URL` / `LEGACY_VSV_WEBHOOK_URL`; tujuan gagal → 502 agar Xendit mengirim ulang.
  4. Pemohon klik `Segarkan`/reload → baris berubah `✓ Lunas`.
  - Tanpa konfigurasi server: `Pembayaran daring belum dikonfigurasi di server. Hubungi tim VentureGo untuk info pembayaran.`
  - Invoice yang sama tidak dibuat ulang (dipakai ulang selama belum kedaluwarsa).

#### Halaman aktivitas, dokumen, notifikasi, profil, & pendukung

- **Riwayat** `/dashboard/riwayat`: menampilkan riwayat transaksi & aktivitas riil dari Firestore (`payments` Xendit, pengajuan `applications`, dan berkas `documents`) dengan filter interaktif `Semua`, `Pembayaran`, dan `Dokumen`.
- **Dokumen** `/dashboard/dokumen`: menampilkan arsip akad pembiayaan (`pricingStatus`, nilai kewajiban, referensi akad final), daftar berkas persyaratan yang telah diunggah beserta status verifikasinya (`Sudah diunggah`, `Diverifikasi`, `Perlu perbaikan`), serta daftar bukti pembayaran lunas (`payments` berstatus `PAID`).

NIS diterbitkan satu kali per Firebase UID **hanya saat staf menerbitkan dokumen akad** (`issueAkadDocument` di tab `Draft Akad`) — sebelum itu tampil `Belum tersedia` + catatan "Terbit setelah dokumen akad diterbitkan."; penerbitan otomatis saat membuka halaman Profil sudah dihapus (read-only `getStudentNumber`). NIS yang sudah pernah terbit (penerbitan lama) tetap tampil. Konten berupa **daftar opsi** (bukan tab/accordion) — tiap opsi membuka **sub-halaman terpisah** dengan header judul + tombol kembali ke `/dashboard/profil`:

Data terkunci jika `pricingStatus: AGREED` atau status pengajuan `ACTIVE`/`COMPLETED`; pemohon diarahkan ke Pusat Bantuan untuk koreksi.

Berkas berada di folder privat Drive; route unduh pemohon memverifikasi token dan `ownerFirebaseUid`, tanpa URL publik. Jika belum ada berkas, tampilkan penjelasan bahwa PDF belum tersedia.

  - Tombol `Keluar` berada di bagian bawah halaman Profil (profil sendiri tetap tanpa header atas). Skeleton loading mengikuti struktur konten masing-masing halaman.

- **Full Cover** (hanya Jepang yang bisa diverifikasi): HPP VSV terdiri dari invoice tagihan LPK + uang saku siswa dan harus sama dengan Nafaqah Draft 2. Rincian itu tersimpan terpisah untuk audit biaya pokok. `Nafaqah`, `Ujrah`, `Ju'alah (jika COE terbit)`, `Tenor setelah keberangkatan (1–36 bulan)` + ringkasan hitung otomatis.
- **Dana Keberangkatan**: invoice tagihan LPK + uang saku siswa harus sama dengan nominal pengajuan setelah dipotong biaya admin 5%; Nafaqah harus sama dengan invoice LPK dan sisa dana bersih otomatis menjadi uang saku/qardh. HPP disimpan terpisah dari Ujrah sehingga total kewajiban akad tetap menghitung Ujrah sesuai akad. Rincian **Lampiran A bersifat tetap dan diturunkan otomatis** (helper `deriveDepartureFinancials` di `src/lib/departure-financing.ts`): Nafaqah = 3 komponen tetap (Pendidikan Bahasa Jepang, Pelatihan Skill Kerja, Pengurusan dokumen) tanpa nominal per baris dengan subtotal = invoice LPK, Ujrah = 2 baris turunan (wakalah 2,4% × 12 bulan + administrasi 5%, penerima `VentureGo VSV`), Uang saku = dana bersih − invoice (= qardh); staf hanya mengisi **Invoice LPK terverifikasi** (uang saku ikut terhitung, read-only), lalu `Jumlah angsuran (1–36)`, `Tanggal angsuran pertama`, `Refund/potongan` + bukti, centang `Qardh sudah diserahkan ke pemohon`, `Referensi akad final yang sudah ditandatangani`, `Catatan penyelesaian`. Total live: `Nafaqah + Ujrah + qardh − refund` — uang saku/qardh selalu ikut dihitung dalam Total Kewajiban tanpa menunggu centang penyerahan; centang `Qardh sudah diserahkan ke pemohon` tetap menjadi syarat status `VERIFIED`/`AGREED`.

**Aturan bisnis penting saat `Simpan`** (semua memblokir dengan pesan spesifik):

- `Terverifikasi` (biaya) mensyaratkan struktur rincian cocok dengan turunan otomatis (3 baris Nafaqah + 2 baris Ujrah identik dengan `deriveDepartureFinancials`, `nafaqahTotal` = invoice LPK, `ujrahTotal` = wakalah + administrasi, invoice + uang saku = dana bersih, `qardhAmount` = uang saku, uang saku > 0 wajib ditandai sudah diserahkan), jadwal angsuran valid (1–36×, tanggal pertama **bulan setelah perkiraan keberangkatan**), dan bukti bila refund > 0. Pengajuan lama dengan struktur rincian format lama harus disimpan ulang lewat tab Draft Akad agar server menurunkan ulang rincian.
- `Disepakati` mensyaratkan **persetujuan pemohon tercatat** (tombol di halaman angsuran) **dan** referensi akad final yang cocok dengan penawaran terbaru. Mengubah penawaran **menghapus persetujuan pemohon** (haru disetujui ulang).
- Full Cover hanya bisa `Terverifikasi`/`Disepakati` untuk tujuan **Jepang**; `ju'alah` diset `COE_ISSUED`, `paymentStartCondition` `AFTER_DEPARTURE`.
- Pembatalan wajib mencatat perhitungan Nafaqah & refund sebelum `Dibatalkan`.
- Setiap simpan menambah `financialPlanHistory` (20 terakhir) + `updatedBy`/`updatedAt`.
- **Dokumen Akad (`.docx`) & Penerbitan NIS:** setelah `pricingStatus` minimal `VERIFIED` dan rincian biaya lengkap, staf dapat meninjau pratinjau dokumen (`GET /api/admin/applications/[id]/akad` via `renderAkadPreviewHtml`, yang membaca isi dan struktur DOCX template) atau menerbitkan dokumen akad (`issueAkadDocument`). Saat diterbitkan, server menerbitkan **NIS** (`VSV-{urutan4}-{tahun}`), membentuk nomor dokumen `<urutan4>/WKL-JPN/VSV-WSB/<romawi>/<tahun>` (Dana Keberangkatan) atau `<urutan4>/WKL-JAL-JPN/VSV-WSB/<romawi>/<tahun>` (Full Cover) yang selaras dengan urutan NIS, mengisi placeholder identitas dan Lampiran A (rincian pembayaran; Full Cover menampilkan invoice LPK, uang saku, Ujrah, dan Ju’alah), baris jadwal angsuran Dana Keberangkatan (nominal tiap angsuran dan sisa kewajiban terisi, tetapi **kolom tanggal jatuh tempo dibiarkan kosong**; kalimat tanggal mulai mengangsur juga tidak diisi karena disepakati saat akad), serta tabel lampiran tanda terima dokumen berisi daftar tetap persyaratan dokumen asli (Akta Kelahiran, Kartu Keluarga, Ijazah SD/MI, Ijazah SMP/MTs/SLTP, Ijazah SMA/MA/SLTA) dengan kolom Asli/Fotokopi, Jumlah, dan Keterangan dikosongkan untuk dicentang saat akad, mengunggah berkas `.docx` ke folder Drive pengajuan, menyimpan metadata `financialPlan.akadDocument`, mengisi `finalAgreementReference` otomatis dengan nomor dokumen bila sebelumnya kosong, dan mengunci rincian biaya (`saveFinancialPlan` & `approveApplicationPricing` ditolak; transisi `setApplicationPricingAgreed` ke `AGREED` tetap diizinkan setelah siswa menyetujui penawaran).
- **PDF akad final:** setelah `pricingStatus: AGREED`, staf dapat mengunggah PDF bertanda tangan melalui tab Persetujuan & Akad. Server membatasi PDF maksimal 4 MB, memeriksa signature berkas, menyimpan ke folder Drive privat pengajuan dengan nama `Akad Wakalah bil Ujrah - <Nama Pemohon>.pdf`, lalu menambahkan metadata `agreementPdf` ke aplikasi. Penggantian PDF mengaitkan file baru ke aplikasi (file lama tetap ada); akses download tetap melalui route terautentikasi.
- **Transisi ke `ACTIVE`:** saat status pengajuan diubah ke `ACTIVE` (sekali, pada transisi), server membaca **NIS** yang sudah terbit (`getExistingStudentNumber`), me-rename folder Drive jadi `<NIS> - <Nama Pemohon>` berwarna **hijau**, me-rename seluruh berkas di folder ke pola `<Jenis> - <Nama Pemohon>`, dan memperbarui mapping `driveFolders` menjadi `stage: 'active'`. Bila NIS belum terbit saat transisi ke `ACTIVE`, promosi folder ditunda dan akan dijalankan otomatis saat staf menerbitkan dokumen akad (`issueAkadDocument`). Operasi Drive bersifat terbaik-usaha dan tidak menggagalkan simpan status.

**Pesan error umum action**: `Pilih status pengajuan yang valid.` · `Catatan internal maksimal 2.000 karakter.` · `Dokumen belum memiliki berkas untuk diverifikasi.` · `Status Disepakati memerlukan persetujuan pemohon dan referensi akad final yang telah ditandatangani.` · `Total kewajiban harus sama dengan Nafaqah ditambah Ujrah.` · `Tanggal angsuran pertama harus berada pada bulan setelah perkiraan keberangkatan…` · `Terbitkan dokumen akad setelah rincian biaya berstatus Terverifikasi.` · `Dokumen akad telah terbit. Rincian biaya terkunci.` · `Dokumen akad sudah terbit untuk pengajuan ini.` · `Status belum dapat disimpan. Coba lagi.` · `Isi invoice LPK pada tab Draft Akad (invoice tidak boleh melebihi dana setelah potongan admin 5%) sebelum menyetujui.` · `Lengkapi jangka waktu dan ketentuan Draft 1, lalu cocokkan penggunaan dana setelah potongan admin 5%: …`

## 8. Catatan Kondisi Saat Ini (Known Caveats)

Daftar ini **harus ikut diperbarui** saat caveat-nya diselesaikan:

1. **Wizard hanya memuat scan KTP** — scan KTP wajib dipilih di langkah Data diri dan diunggah ke Drive bersamaan saat submit; dokumen lain diunggah setelah submit di `/dashboard/unggah-berkas` dan pengajuan baru selalu memulai slot lain `NOT_UPLOADED`.
2. **Hanya Scan KTP yang memblokir submit** — penanda `*` pada dokumen wajib lain (Pas Foto, KK, Ijazah) tetap advisory dan diverifikasi staf setelahnya. Validasi server mengwajibkan KTP di kedua produk (`Dokumen Scan KTP wajib diunggah.` / `Dokumen KTP siswa wajib diunggah.`); pengecekan `required` lama hanya berjalan untuk Full Cover.
3. **Ganti dokumen tidak menghapus file lama** di Drive (file lama tetap tersimpan di folder yang sama).
4. **VIP belum punya pendaftaran & kontrak** — staf mencatat mitra dan transaksi di `/admin` → Mitra VIP; belum ada pendaftaran mitra dari aplikasi, kontrak/akad mitra, top-up Xendit, maupun laporan PDF bulanan. Rencana ada di `docs/usulan/2026-11-vip-pendaftaran-dan-akad.md` (pendaftaran rinci, kontrak seperti siswa, akad diperbarui sesuai fikih muamalah).
5. **Banner sukses/gagal pembayaran** di `/dashboard/pembayaran` hanya muncul bila parameter `?payment=` ada di URL (return URL Xendit saat ini tidak menyertakannya); andalkan `Segarkan`/webhook.
6. **Kuota daftar admin maks 500 pengajuan & 500 pembayaran terbaru** — pencarian dan filter berjalan di klien atas 500 pengajuan terbaru.
7. **Tahap 5 (Pencairan dana)** pada `Alur progress` tidak pernah jadi tahap `SEKARANG`.
8. **Tidak ada halaman login admin** — staf masuk lewat `Masuk dengan Google` di welcome `/`; allowlist & cookie tetap berlaku. `vworksofficial@gmail.com` dan `demo.admin@venturego.id` terdaftar di `isStaffEmail`.
9. **Record lama milik akun anonim tidak bisa diakses pemohon** setelah migrasi ke Google; admin masih melihatnya di `/admin`, tetapi tidak ada jalur klaim karena email anonim tidak tersimpan. Jangan hapus record tersebut.
10. **Kredensial akun demo ada di `src/lib/demo-accounts.json`** (`demo.user@venturego.id` / `UserDemo123!` dan `demo.admin@venturego.id` / `AdminDemo123!`), tetapi **tidak ada lagi tombol demo** di halaman awal (semua mode hanya `Masuk dengan Google`). Akun demo masih bisa dipakai lewat script seed bila diperlukan.
11. **NIS hanya diterbitkan saat staf menerbitkan dokumen akad** (`issueAkadDocument` di tab `Draft Akad` pada `/admin`) melalui transaksi Firestore pada `studentProfiles` dan `systemCounters` — urutan 4 digit NIS yang sama langsung dipakai untuk membentuk nomor dokumen akad (`<urutan4>/WKL[-JAL]-JPN/VSV-WSB/<romawi>/<tahun>`). Transisi status `ACTIVE` dan promosi folder Drive kini hanya membaca NIS yang sudah ada secara read-only (`getExistingStudentNumber`); penerbitan otomatis saat membuka halaman Profil/Kartu tetap dihapus (read-only). NIS lama yang sudah terbit tetap tampil. Tidak perlu migrasi massal dokumen pengajuan; nomor yang sudah diterbitkan tetap sama untuk UID tersebut.
12. **PDF akad final belum tersedia sampai staf mengunggah dokumen bertanda tangan** dari tab Persetujuan & Akad di `/admin` setelah biaya berstatus `Disepakati`.
13. **Mode development terhubung langsung ke project Firebase Cloud di `.env.local`** (tanpa memerlukan emulator lokal). Untuk login Google di lokal, gunakan `http://localhost:3000` (akses ke `127.0.0.1` otomatis dialihkan ke `localhost` karena Firebase hanya mengizinkan domain `localhost` secara bawaan). Login Google langsung butuh `NEXT_PUBLIC_GOOGLE_CLIENT_ID` dan origin `http://localhost:3000` terdaftar di _Authorized JavaScript origins_ OAuth client; tanpa env itu dipakai popup Firebase.
14. **Mengganti PDF akad mengaitkan file baru ke aplikasi; file versi sebelumnya tidak dihapus dari Google Drive** agar arsip lama tidak terhapus. Karena nama file kini standar (`Akad Wakalah bil Ujrah - <Nama Pemohon>.pdf`), versi lama dan baru dapat bernama sama dan dibedakan oleh waktu ubah di Drive.
15. **Folder & file lama tidak dimigrasi massal** — hanya root yang di-rename in-place; folder draft lama (format `<Nama> · <uid6>`) dan nama file lama tetap seperti aslinya sampai pengajuan terkait mencapai `ACTIVE` (saat itu folder di-rename `<NIS> - <Nama>`, diwarnai hijau, dan seluruh file di dalamnya ikut di-rename ke pola standar).
16. Halaman 404 (`not-found`) masih berbahasa Inggris.
17. **Penerusan webhook bersama akun Xendit** — `trm-` (Turrima) dan `vsv-` (36 kontrak siswa di app VentureGo versi lama, database terpisah) diteruskan, bukan diproses. Data kontrak lama **belum dimigrasi** ke Firestore; selama itu app lama harus tetap hidup di alamat `vercel.app`-nya. `XENDIT_CALLBACK_TOKEN` harus sama di semua app yang berbagi akun Xendit.
18. **Kebijakan Privasi & Syarat Layanan masih draf** — perlu ditinjau legal/DPS (nama badan hukum, email layanan) sebelum dipakai untuk verifikasi merek Google atau toko aplikasi.
19. **Pengajuan Dana Keberangkatan lama menyimpan struktur Nafaqah/Ujrah format lama** — server kini menurunkan ulang rincian dari principal + invoice LPK, sehingga record lama yang belum disimpan ulang ditolak saat `Setujui` / `Tandai Disepakati` / penerbitan dokumen dengan pesan yang mengarahkan staf ke tab Draft Akad. Tidak ada migrasi massal: struktur lama otomatis terganti saat staf menyimpan rincian berikutnya (satu kali simpan), dan dokumen akad yang sudah terbit tidak berubah. Field `financialPlan.principal` bersifat aditif (baru diisi saat disetujui/simpan).
